**Действие:** Завершать функции-заглушки (SelfUpdater в proteus-core) и переносить в них дублирующийся код для сохранения чистоты архитектуры.

## 2026-07-25 - AiOrchestratorService State Machine
**Инсайт:** При реализации `AiOrchestratorService` была выявлена необходимость использовать асинхронные блокировки (`tokio::sync::Mutex` вместо стандартных `std::sync::Mutex`). Если используются стандартные мьютексы, компилятор не позволит передавать их через точки `await`, так как они не реализуют `Send` безопасно для асинхронного контекста. Это критично для конечных автоматов, которые выполняют асинхронные операции в своих состояниях.
**Действие:** Всегда использовать `tokio::sync::Mutex` или `RwLock` в асинхронных стейт-машинах и сервисах (особенно в `proteus-ai` и `proteus-core`), где требуется удержание блокировки через асинхронные вызовы.

## 2026-07-29 - Missing Timeout on Async Network Calls
**Инсайт:** При выполнении сетевых запросов через `tokio::net::TcpStream::connect` или другие низкоуровневые средства, если не обернуть вызов в `tokio::time::timeout`, он будет использовать системный таймаут (который может составлять 2+ минуты). В `check_via_socks5` это приводило к долгим зависаниям оркестратора на мертвых прокси, а в юнит-тесте `test_check_tcp_timeout` — к длительности теста свыше 2-х минут.
**Действие:** Всегда явно ограничивать время выполнения асинхронных проверок (например, через `tokio::time::timeout`), особенно когда они запускаются параллельно в цикле.

## 2026-08-01 - Missing Timeout on Async Network Calls in Probe
**Инсайт:** Использование `tokio::net::TcpStream::connect` и `lookup_host` без явного оборачивания в `tokio::time::timeout` приводило к долгим зависаниям и неконтролируемым таймаутам (зависело от ОС) внутри метода зондирования. Оборачивание всей асинхронной задачи в timeout не решает проблему зависания низкоуровневых операций до завершения таймаута всей задачи.
**Действие:** Добавлен внутренний 10-секундный таймаут для всех низкоуровневых сетевых операций (DNS, TCP, HTTP) в `check_target` сервиса зондирования.
## 2026-08-04 - Missing Workspace Dependency in proteus-core
**Инсайт:** При выполнении сборки/тестирования проекта оказалось, что пакет `proteus-core` использовал компоненты из `proteus-engine` (например, в `manager.rs`), но эта зависимость не была указана в `proteus-core/Cargo.toml`. Это приводило к ошибке компиляции E0432.
**Действие:** Всегда проверять наличие необходимых зависимостей в манифестах crates при использовании типов из других модулей воркспейса, особенно если в коде присутствуют явные `use`.

## 2026-08-05 - Event-driven Orchestrator Pattern
**Инсайт:** Использование множества отдельных функций для перехода между состояниями (например, `begin_fingerprinting`, `complete_fingerprinting`) в `AiOrchestratorService` нарушало принципы строгой конечной машины (FSM).
**Действие:** Использовать единый enum событий (например, `OrchestratorEvent`) и единственный диспетчер `dispatch(event)` для переходов между состояниями. Это гарантирует жесткий контроль за правилами переходов в одном месте.
